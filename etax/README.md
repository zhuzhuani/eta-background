# Etax（Eta 助手·后台版）· 源码版

基于上游 [Mangi-11/Eta](https://github.com/Mangi-11/Eta) `v3.3.3`。
以前的做法是把官方 APK 的 dex 反编译、手工插入调用再打包；现在所有接线都写在源码里，
直接从源码编译出 APK，不再依赖 `dexopt2/classes.dex`。

## 当前版本：引擎生命周期与资源回收（2026102702）

- `screen_finish(notify)` 立即停止图像监听、断开截图表面并释放 ImageReader、图像和位图；只短暂保留承载已完成 App 的虚拟屏。截图常规路径直接从原生缓冲复制到位图，省去一份完整像素数组；兼容末行缺失填充的 ROM。
- 点击完成通知仍由 Android 将目标 App 打开到主屏。已有无障碍窗口事件只发送有界、限频的提示，Root 必须核实跟踪任务已移出且旧屏为空，才回收旧屏。事件缺失时由原巡检兜底，不因收到提示就销毁屏幕，不自动将 App 拉回后台。
- 旧屏和 worker 清理成功后立即归还 Root 名额；清理未确认仍保留占位并重试。临时截图仅清理该 worker 的私有目录，不清理用户指定的输出路径。
- 同一 App 的后续任务优先接管已完成、已交还所有权、尚未开始回收的屏幕，再恢复采集；旧会话的迟到清理不能关闭新所有者。正在清理或仍有请求执行的屏幕不可接管。
- 已完成屏幕仍最多保留约 1 分钟，新任务需要容量时可提前回收；重复清理请求不延长保留时间。超时/容量回收仍遵循 Android 的任务移除行为，不承诺第三方 App 永久驻留。没有新增常驻服务或高速轮询；每轮巡检复用一份任务快照，取消逐轮 `pidof` 子进程查询。

本轮真机重点复测：完成后立即点击网心云通知、从桌面打开目标 App、同一 App 连续两次后台任务、两个 App 并行且先完成的一项转到前台。确认没有被 ETA 拉回后台或触发延迟重启，后续任务能取得空闲名额。截图恢复、跨屏生命周期和回收时机仍需 OPPO Find X9 Ultra / ColorOS 17 实测；本地测试不能代替 ROM 验证。

### 继续保留的稳定性策略（2026102701）

- 最多同时执行两个任务。其他请求保存在有界队列中（沿用总共 8 个未结束请求的容量），排队期间不启动模型、摄取线程或虚拟屏；通知和会话列表显示等待状态。相同 App 继续串行使用。
- App 层和 Root 层的虚拟屏上限均为 2；清理未确认的屏仍占位。取消排队任务不影响已运行任务。Root 层保留必要的回收确认与退避重试。
- 删除延迟窗口适配、兼容模式进程重启及对应轮询。接受第三方 App 少量留边，ETA 不再为了铺满屏幕请求重建 App 页面。第三方 App 自身及 Android 的生命周期仍由系统管理。
- 删除 CPU/虚拟屏唤醒锁、续期和专门的息屏电源处理。收到息屏事件后暂停任务，后续模型请求/操作在已有检查点等待；亮屏不自动恢复，解锁后手动继续。正在进行的操作不回滚，也不重放有副作用的工具请求。
- 恢复后拒绝使用旧观察结果直接点击、滑动或输入，必须先成功重新读取界面或截图。已有模型失败重试在暂停检查点等待，不在息屏期间持续请求网络。
- 只在实际运行时请求系统实时活动并播放边缘动画；暂停和排队保留原任务卡片及控制。任务完成仍原位更新并点击打开对应 App，同时提供独立的“打开聊天记录”按钮查看结果与过程。
- 会话列表复用 Runtime 状态；语义状态不变时不因流式正文重建所有摘要。切换会话保留最多 8 个会话的轻量阅读/输入界面状态，不保留额外执行器或截图。
- 本轮不增加后台服务或 CI 工作流。以下各小节记录的是历史版本行为，冲突时以本节为准。

真机重点复测：网心云任务完成后点击原通知，保持前台观察不应由 ETA 触发延迟重启；网心云与滴滴同时运行并提交第三项，前两项不被取消；息屏后解锁应仍暂停，手动继续后先观察页面；切换会话返回原阅读位置。通知呈现、跨屏 App 生命周期和系统回收仍需在 OPPO Find X9 Ultra / ColorOS 17 验证。

## 改了什么

| 位置 | 作用 |
|---|---|
| `app/src/main/java/com/eta/shadow/` | 影子代码（通知流式输出、后台虚拟屏工具、观察者、引擎自启 `Engine.java`） |
| `etax/engine/` | 内嵌的 root 引擎（dex + 启动脚本），编译时打进 APK assets，装完授 root 自动拉起 |
| 10 个上游 Kotlin 文件，每处带 `// etax` 注释 | 接线点，对应原来 dex 里的 10 处注入，外加任务开始和结束两个钩子 |
| `app/build.gradle.kts`、`AndroidManifest.xml` | 包名 `io.github.mangi.etax`，显示名「Eta 助手·后台版」 |
| `etax/check_hooks.sh` | 构建前检查 12 处接线都在，少一处就让构建失败 |
| `.github/workflows/etax-build.yml` | 在 GitHub Actions 上编译 APK |

## 编译（GitHub Actions）

1. 在 GitHub 上新建一个**私有**仓库，把整个目录推上去，分支名用 `etax-3.3.3`。
2. 仓库 Settings → Secrets and variables → Actions，添加这 4 个 Secret（用你现在的 `etax.jks`，
   这样新包才能直接覆盖安装、不丢数据）：
   - `ETAX_KEYSTORE_BASE64`：`base64 -w0 etax.jks` 的输出
   - `ETAX_STORE_PASSWORD`：keystore 密码
   - `ETAX_KEY_ALIAS`：别名，用 `keytool -list -keystore etax.jks` 查看
   - `ETAX_KEY_PASSWORD`：key 密码
3. 推送后到 Actions 页面打开 **Etax Build**，跑完后在页面底部下载 APK，大约 15–25 分钟。

不配置 Secret 也能编译，只是会用临时证书签名，装之前要先卸载旧的 etax。

**root 引擎（源码内嵌 + 自启）**：引擎**源码**在 `etax/engine/src/`（`VDrive.java`、`McpEndpoint.java`、
`UiaProbe.java`），加上 `build_engine.sh` 和部署脚本（`vd.sh`、`install_vdrive.sh`、`check_pair.sh`）。
CI 用 `javac + D8` 从源码现编出 `vdrive.dex`（不是 Gradle 模块），版本串从 `VDrive.java` 的 `BUILD`
常量抽取写入 `vdrive.version`，一起打进 APK 的 assets。**不再提交二进制 dex，以源码为准。**

装完 APK 后，无障碍服务一连上、或第一条 `screen_*` 工具调用时，`com.eta.shadow.Engine` 会自动用 `su`
把这些文件释放到 `/data/local/tmp/eta/` 并跑 `vd.sh` 把引擎拉起来 —— **装完授一次 root 就能用，不用再手动部署**。

- 引擎需要 **root**：未 root 的手机 `su` 会失败，`screen_*` 会提示去授权（通知栏流式输出那条链路不吃 root，照常可用）。
- 自启幂等：引擎在跑就不动它（`vd.sh status`）；换了新版（dex 变了）会自动重铺并重启；运行中 build 与内置版本不符也会强制重启到内置版。
- 工具链会影响 dex 字节：CI 用现成 JDK/D8，产物与本地逐字节不一定相同，但功能等价、且 APK 自洽（App 首次运行会把手机上旧 dex 换成 APK 内这版）。想字节级复刻需钉死 JDK/r8/android.jar 版本。
- 升级引擎：改 `etax/engine/src/` 源码并把 `VDrive.java` 的 `BUILD` 常量改成新 stamp，CI 自动现编、配对。
- 仍可手动管理：`sh /data/local/tmp/eta/vd.sh`（重启）、`vd.sh stop`、`vd.sh status`、`check_pair.sh`（配对校验）照常能用。


## 后台多任务（3.3.4 扩展）

- 电源键入口提交后立即建立在途记录。App 用同一会话身份恢复已有事件并订阅后续事件；完成归档按 run ID 去重。关闭入口不取消任务，新一次唤醒拥有独立会话。
- `BackgroundScreenTools` 为每次运行绑定独立工具实例，`ScreenLeaseRegistry` 保留最多三个屏幕名额。同一应用等待当前所有者释放；不同应用并行。第四个不同应用需要屏时取消最早取得名额的任务，直到引擎确认旧屏清理后才分配新名额。
- `VDrive` 负责本地传输及有限容量的会话表，`VDriveWorker` 保留原引擎的 Android 操作实现。每个 worker 有独立 Handler、显示对象、输入状态、截图目录和清理状态。请求携带不可复用的 `sessionId`，已释放会话拒绝迟到请求。
- 活跃任务每 30 秒续期；App 进程消失后引擎回收过期会话。正常 `screen_finish(mode=notify)` 可继续停留最多一分钟，后续任务优先回收这些已完成的屏。
- 每个活动任务有独立系统实时通知，分别显示流式进度、打开聊天、暂停及停止；旧 Android 仍可使用 App 胶囊。支持系统允许的 promoted ongoing 显示。频道为静音 DEFAULT 频道；系统通知权限和 ColorOS 状态栏/流体云布局仍由系统管理。
- 边缘流光复用官方组件，亮屏绘制、息屏移除窗口；后台展示不申请保持屏幕常亮。

引擎协议增加 `sessionId`、`keepalive`、`validate`、`release_session`。无会话标识的 MCP 请求继续使用独立的兼容会话。`release_session` 的成功响应代表清理已确认，不能以网络超时推断已释放。设备动作可能已经发生，重连只恢复记录，不自动重放操作。

相关回归测试：`ScreenLeaseRegistryTest`、`AssistantRunRecoveryTest`，以及 Runtime 会话、恢复、通知和浮层测试。虚拟屏输入焦点、后台运行及 ColorOS 流体云表现需要在真实 Root 设备验证。

### 系统流体云与窗口恢复（2026102602）

- Android 16 QPR1 及以上只使用系统实时通知呈现任务，不再叠加 App 自绘胶囊或完成浮窗；边缘流光独立保留。旧 Android 版本继续使用原胶囊。
- 运行通知仍为同一个 ID `1107`。卡片内容跳转所选任务的聊天；多任务时提供切换、暂停/继续、停止当前任务。每个操作绑定不可复用的 run ID，迟到操作不影响后续任务。
- 流式更新同时刷新前台服务持有的通知快照，避免该快照一直停留在启动时的通用文案。单元测试确认只有一个通知记录；ColorOS 是否额外呈现普通通知须由真机复测，不能仅凭截图断言已消除系统层重复。
- `screen_finish` 只负责屏幕收尾，不再额外发布一条打开目标 App 的通知。最后完成的结果在前台服务释放后替换同 ID 的运行通知；已完成状态不继续申请系统实时活动。
- 点击/长按系统胶囊如何展开由 ColorOS 决定；点击其卡片进入聊天。系统可将同一实时通知同时呈现在状态栏及下拉区域，不能通过删除通知来保留其流体云。
- 应用显式移回主屏，或用户从桌面重新打开已停留在虚拟屏的应用时，清除该任务的窗口边界、应用边界、dp 尺寸和密度覆盖，恢复主屏全屏配置。使用 Root WindowContainerTransaction，不改手机全局分辨率、不强制停止第三方应用。ROM 不支持接口时记录失败并尝试清除像素边界；兼容缩放是否消失须由真机验证。
- 新增 `AgentSystemNotificationTest`，覆盖单一通知、聊天跳转不串任务，以及完成通知与前台服务退出的先后顺序。

系统接口参考：[Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update)；[ColorOS 流体云操作](https://www.coloros.com/article/A00000075/)。

### 屏幕回收与兼容模式修复（2026102603）

- 屏幕关闭改为异步发起、确认后释放名额；失败后持续重试，不再三次失败就永久保留占用。`screen_finish` 成功即可交还应用所有权，无须等待模型回答结束。同一任务的屏幕操作串行，不同任务仍可并行；引擎明确返回启动前 `CLEANUP_PENDING` 时自动等待重试，超时或未知结果不会重放设备操作。
- 已完成的屏不再保持唤醒锁；亮屏时检查目标应用是否已回到主屏，及时清除虚拟屏配置。若同一个可见任务仍被系统标记为尺寸兼容模式，调用 Android 兼容重启按钮对应的 `TaskOrganizer.restartTaskTopActivityProcessIfVisible` 接口，清除旧兼容配置并重建界面，可能短暂重绘。普通全屏任务、隐藏任务及已换身份的任务不触发重建。ColorOS 的实际显示仍需真机验证。
- 截图改为保留最新原生图像，仅在请求截图时复制像素，避免逐帧复制整屏；完成时立即释放图像缓存。实际耗电变化未作真机测量。
- 首条任务检查点改为后台写入；执行和取消归档都等待该写入完成，保持记录顺序并避免取消后的旧记录复活。
- 显示等待应用、回收屏幕、打开应用、恢复显示及等待模型等状态。设置页可检查后台通知权限、跳转系统设置；通知被关闭时使用已有浮窗回退。
- 设置 → 关于 → 导出运行诊断：仅导出设备/版本、通知可用性、引擎会话数量、显示恢复结果及最多 120 条白名单状态事件；不导出聊天、截图、密钥、任务标识或目标应用名，用户选择本地保存位置。

补充回归覆盖：回收连续失败超过三次后的恢复、完成后让出同一应用、明确回收中响应的启动重试、兼容重建条件、首条记录与取消归档顺序、诊断字段过滤及通知关闭状态。

### 后台收尾、独立通知与息屏执行（2026102604）

- 后台工具不再提供切回主屏的收尾方式；旧会话中的 `handover` / `background` 收尾参数在工具与引擎入口归一为 `notify`，直接后台 `handover` 命令被拒绝。MCP 的显式前台操作入口仍兼容。目标应用仅在用户点击完成卡片或自行从桌面打开时出现在主屏。
- 主屏配置恢复延后到同一任务在物理主屏亮起且持续获得焦点时进行，后台结束时不直接修改窗口。尺寸兼容重建也必须满足该条件，减少临时移屏引起的重绘和闪现。
- 每个任务独立卡片和控制入口，取消系统通知中的“切换任务”按钮。一个活动任务承担已有前台服务通知，其余独立发布；完成时在原通知 ID、图标和原生进度样式上直接显示“任务已完成”，不另发完成通知。终态事件立即刷新，不等待其他任务结束或后续归档回调；前台服务转交下一任务时先 detach，避免系统移除已完成卡片。
- 运行卡片打开对应聊天，完成卡片打开该任务最后成功操作的 App；无目标 App 时回退到聊天。保留最近三项完成卡片，新一批任务开始时清理旧完成卡片。用户取消的卡片不会被迟到的归档通知重新发布。普通流式更新每 750 毫秒合并一次，未变化卡片不重复发布。ColorOS 控制顶端胶囊数量及任务完成后的收起行为，应用无法指定系统布局。
- 已有执行服务持有可超时的 CPU 唤醒锁，覆盖模型等待与结果保存，结束即释放。虚拟屏使用独立显示组和 `ALWAYS_UNLOCKED`，只有确认显示组与主屏不同，才申请绑定该虚拟屏的显示唤醒锁；若 ROM 不支持，则记录诊断，绝不对主屏申请亮屏锁。该能力仍需在目标 ColorOS 真机息屏测试，不能用 JVM 测试保证 ROM 行为。
- 精简重复处理：通知选中状态字段合并为一份任务快照；屏幕心跳与清理共用三线程调度器；删除额外的完成屏巡检，交由已有巡检处理；状态复位统一在工具出口执行。正常回收从 150 毫秒开始确认，持续失败逐步退避，减少切换延迟与空转。启动及移屏等待支持及时取消。
- 诊断增加物理屏状态、执行 CPU 锁、虚拟屏独立供电能力计数及电池优化豁免状态；仍不记录聊天、密钥、截图或目标应用名称。

验收重点：完成网心云/滴滴后台操作时主屏无闪现；三任务各自展示进度，某项完成时原卡片立即更新且点击打开正确 App，其余任务继续；运行中锁屏后再唤醒查看新增步骤及结果；任务全部结束后释放电源和虚拟屏资源。
